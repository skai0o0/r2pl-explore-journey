# M3.6 — realtime delivery optimization review

**Status, 2026-10-10:** telemetry and bottleneck investigation completed for the synthetic PostgreSQL-backed protocol-v1 fixture. The 1,000-client, 250-actions/s hotspot **does not pass a sustained low-latency delivery gate**. No protocol or architecture optimization was adopted. M4 remains unauthorized pending owner review. This report makes no 10,000-CCU or production gameplay claim.

## Scope and retained contracts

The existing Colyseus gateway, one in-process writer per sector, PostgreSQL full-chunk transaction baseline, committed ACK, durable outbox, per-school projection, bounded outbound queue, and v1 contiguous delta revision semantics remain. Synthetic identity, `fixture-credit`, generic school slots 0/15 and rule version 0 are test-only. The official roster and C-08 visibility policy are still pending. Protocol-v2 batching remains isolated; no Redis or distributed authority was added.

## Telemetry corrections and correlation

The earlier aggregate `sector_queue_wait_ms` mixed command, subscription/snapshot and relay operations. Its p95 was therefore from a different population than client ACK p95, and could exceed ACK p95 without a contradictory action trace. M3.6 labels queue wait and execution by work kind, while preserving the aggregate for compatibility. `command_ack_ms` starts at gateway callback entry; client ACK timing starts at the generator's send. PostgreSQL `durable_transaction_ms` includes transaction work but excludes prior sector wait. `commit_to_claim_return_ms` ends when a batch claim query returns; later events in that batch can wait behind earlier publications. `ackSinkSendResolvedMs` and `deltaSinkSendResolvedMs` mean the Colyseus sink call resolved, **not** socket receipt. Client receipt timestamps are captured separately. All correlation stages use same-host monotonic clocks in separate Node processes; database timestamps are not mixed into the trace arithmetic. Correlation IDs are the synthetic command keys and traces are bounded to 32 sampled first submissions. Retry samples do not overwrite the original trace.

Representative correlated actions from [`M36_1000_hotspot_indexed_10s_250r_trialtrace2.json`](benchmarks/M36_1000_hotspot_indexed_10s_250r_trialtrace2.json) show the shift in delay (milliseconds):

| Action index | Gateway→sector | Sector→commit | Commit→client ACK | Commit→claim return | Claim return→projection | Projection→delta enqueue | Commit→client delta |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 0 | 0.3 | 14.8 | 0.7 | 1.2 | 0.2 | 19.7 | 22.4 |
| 1,000 | 865.8 | 4.1 | 0.1 | 11,092.3 | 238.9 | 0.1 | 11,341.6 |
| 2,000 | 1,688.9 | 4.9 | 0.3 | 11,699.6 | 34.1 | 0.0 | 11,737.7 |

The postcommit delivery wait is real even where the database transaction and ACK enqueue are short. For a batched claim, claim-return→projection includes time spent on preceding events. The raw JSON preserves every captured stage and missing stages for no-change commands.

## Bottleneck evidence

In three independent 20-second trials per pattern, the server and generator were separate Node processes on the **same Windows host** (Intel i5-13400F, 16 logical CPUs, 34.2 GB RAM, Node 24.19.0) using loopback Colyseus sockets and isolated PostgreSQL 16.15. Each of 1,000 clients subscribed to one chunk in one of two synthetic schools. Balanced actions span 16 sectors; hotspot sends 70% to one sector/chunk. PostgreSQL has durability settings enabled. Client replicas were checked against exact authoritative masks and fog. The 30-second post-ACK drain bound was used for these trials. `actionSeconds` in older artifacts is **send start through all ACKs**, not generator dispatch; trial 3 records both separately. Sampled send timestamps in trials 1–2 span approximately 19 seconds between action 0 and action 4,750, consistent with the target schedule.

| Workload, 5,000 actions | Trial | Client ACK p95 | Commit→client visible p95 | Time until all ACKs | Post-ACK convergence | Outbox at end |
|---|---:|---:|---:|---:|---:|---:|
| Balanced, 250/s | 1 | 112.7 ms | 1,601.9 ms | 20.01 s | immediate | 0 |
| Balanced, 250/s | 2 | 59.7 ms | 2,363.5 ms | 20.01 s | immediate | 0 |
| Balanced, 250/s | 3 | 52.9 ms | 1,090.8 ms | 20.01 s | immediate | 0 |
| Hotspot, 250/s | 1 | 5,402.7 ms | 25,081.0 ms | 25.54 s | 21.62 s | 0 |
| Hotspot, 250/s | 2 | 4,713.5 ms | 24,818.4 ms | 25.20 s | 21.50 s | 0 |
| Hotspot, 250/s | 3 | 4,826.8 ms | 24,863.0 ms | 25.03 s | 21.37 s | 0 |

Trial 3's measured dispatch was 19.995 s balanced and 19.998 s hotspot, or 250.1 and 250.0 submitted actions/s. The hotspot's longer ACK phase is server completion delay, not missed generator pacing. All 5,000 actions received ACKs, exact replicas converged, ten duplicate retries returned the saved result, ten conflicting-payload retries were rejected, and the outbox eventually drained. This **does not** mean the 250/s hotspot is sustainably served at acceptable latency: backlog accumulated during input and the 30-second drain saved the final-state check. The hotspot's trial-3 sampled peak was **4,332 pending outbox events**, versus **241** balanced. Separate 10-second samples peaked at 2,197 and 2,267 hotspot versus 242 balanced; all eventually reached zero. The 20-second trial-3 hotspot sent 1,189,358 outbound frames for 1,182,338 fanout recipients, versus 263,020 frames balanced. Application-level outbound bytes were about 50.3 MB hotspot. Server and generator consumed 34.66 and 26.73 CPU-seconds respectively over the 49.64-second hotspot run; they share physical CPUs. Server RSS at the end was 237.6 MB. A 10-second sample rose from 157.5 to 219.2 MB RSS while backlog grew and drained; this short interval does not prove long-term memory boundedness.

The 20-second hotspot trial-1 server measured command queue wait p95 **5.39 s**, relay queue wait p95 **0.009 ms**, transaction p95 **20.1 ms**, pool wait p95 **0.23 ms**, outbox claim query p95 **5.95 ms**, projection decode p95 **0.019 ms**, delta encoding p95 **0.016 ms**, fanout enqueue p95 **0.60 ms**, and commit→claim-return p95 **25.0 s**. Mark-delivered p95 was 1.06 ms. Socket buffered-byte samples were zero and outbound in-process queue depth peaked at two frames; neither proves the operating-system send path has spare capacity. A raw Node CPU profile ([profile](benchmarks/profiles/CPU.20261010.113219.27636.0.001.cpuprofile)) attributed 7.29 self CPU-seconds to `writev`, 0.62 to outbound drain, 0.38 to enqueue, 0.28 to GC, and 0.21 to mutation apply; idle self time was 7.28 seconds. Its profiled 10-second hotspot run failed the original 10-second convergence bound with 288 outbox events pending. Together, the data point to v1 per-recipient socket write amplification and serial relay/fanout work as the dominant tested constraint. They do not isolate a single universal throughput limit or rule out shared-host CPU scheduling effects. PostgreSQL pool contention, chunk locks and binary projection/encoding were not the dominant measured delays in this workload.

Two 4-second 750-actions/s hotspot bursts submitted 3,000 actions each. Trial 2 measured 3.999 s dispatch (750.1/s), but all ACKs required 13.14 s, client ACK p95 was 8.42 s, visible p95 was 16.62 s, and convergence took another 15.83 s; the sampled backlog peaked at 2,950 before fully draining. Trial 1 was similar (ACK p95 10.18 s, visible p95 16.28 s). These are burst recovery measurements, not evidence that 750/s is sustainable. Raw artifacts are `docs/benchmarks/M36_*.json`; all network tests used separate processes on one host, not an independent generator host.

## Controlled changes and decision

| Candidate | Measured outcome | Decision |
|---|---|---|
| Split command and relay/snapshot sector queues | One 1,000-client/10-second hotspot trial reduced commit→visible p95 to 10.0 ms, but client ACK p95 regressed to 14.34 s and command queue wait p95 to 14.32 s; four outbox rows still pending at summary. | **Rejected and reverted.** Publication competed more aggressively with commands; one trial is insufficient to justify architectural separation. |
| Synchronous common-path sector relay | One trial: ACK p95 2.04 s, 265 pending at the original cutoff, versus instrumented baseline 1.97 s and 202 pending. | **Rejected and reverted.** No reliable benefit. |
| Skip a microtask for synchronous sink sends | One trial: ACK p95 1.76 s but 421 pending, within baseline variance and worse delivery backlog. | **Rejected and reverted.** No safe measured improvement. |

The retained changes are telemetry, a more accurate load harness, bounded correlation traces, a phase-labelled sector histogram, outbox/backlog/resource sampling, and focused recovery/backpressure tests. The durable command, relay scheduling, fanout algorithm and protocol-v1 wire format are unchanged. Reducing v1 frame count requires a separately approved versioned contract; M2.6's v2 batching experiment cannot be promoted from these results. A direct postcommit notification must preserve durable outbox replay, deduplication and ordered school/chunk revisions; it was not introduced without a correctness design. ADR-011 full-chunk writes remain the approved revisitable baseline.

## Recovery, tests and remaining risks

The new PostgreSQL test commits three mutations with publication paused, replaces the authority/core, drains and deduplicates the backlog, checks exact own-school snapshots and school-15 isolation, then sends ten burst RESYNC requests. A second test blocks one sink until its bounded queue closes, while a healthy subscriber receives all eight ordered deltas and the outbox drains. Existing M3.5 tests cover forced process termination after commit before ACK, same-key replay after restart, concurrent wallet/chunk writes, malformed-event quarantine and snapshot recovery. The full disposable-PostgreSQL suite passed **26/26**; TypeScript strict check, Biome lint and client build passed. No dependency was added. First-party source is 28 files/135,238 bytes, tests 8/73,102 bytes, scripts 12/64,518 bytes; client bundle 535,489 raw/133,880 gzip bytes.

Remaining capacity risks: same-host generator/server/database interference, sustained hotspot backlog growth under 250/s v1 traffic, high visible latency even when balanced traffic eventually drains, no long-duration memory plateau proof, no independent-host run, and no production workload distribution. The current fixture only has one authority process; multiworker fencing/publication is not validated. No live campaign or physical reward feature was enabled.

The synthetic durability/correctness contract remains sound, but the proposed 250/s hotspot delivery gate is not met at usable ACK/visible latency. An owner decision can scope a small synthetic slice after C-01/C-08 and fixture identity/rule approvals in [`M4_PRODUCT_DECISION_CHECKLIST.md`](M4_PRODUCT_DECISION_CHECKLIST.md); C-02/C-03/C-04/C-09 remain disabled unless that slice exercises them. Stop for owner review here.
