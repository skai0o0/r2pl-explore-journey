# M2.6 — ordered realtime delta batching experiment

**Status, 2026-10-10:** the owner accepted this as a completed experiment. The branch `experiment/m2.6-batching` remains isolated, and version-1 per-action deltas remain the default. The owner has not approved batching for production, higher-capacity readiness, or M4. M3.5's durable pipeline evaluation is in `M3.5_REPORT.md`.

## Contract and isolation

The branch adds an opt-in version-2 `DELTA_BATCH` frame: one school/chunk base revision and 1–256 ordered five-byte records. Every record advances one revision, including repeated updates to the same tile. Version-1 subscribers and the version-1 golden frames remain compatible. The server still sends private ACKs immediately through the outbound queue, independent of the batch timer. A gap triggers RESYNC and an authoritative snapshot; duplicate/overlapping records are handled without replaying an already applied prefix. Resubscribe, resync, unsubscribe and disconnect invalidate pending frames. A session holds at most 1,024 pending records, with the existing outbound frame/byte hard limits. `PROTOCOL.md` defines the exact wire layout.

This experiment runs only the M2 synthetic EXPLORE rule with slots 0 and 15. It has no durable gameplay command, reward, identity provider or approved production visibility rule. The M3 transaction service is deliberately separate. A legacy server rejects a version-2 subscribe; production rollout would need capability negotiation or an explicit client downgrade path.

## Method and evidence

The server and generator ran as **separate Node.js processes on the same Windows desktop**, using loopback Colyseus sockets. Host: Intel i5-13400F, 16 logical CPUs, 34.2 GB RAM, Node 24.19.0. PostgreSQL was stopped during this experiment. Each case connected 1,000 synthetic clients, two schools, one subscribed chunk per client, and used scan fanout. Balanced actions spanned 16 sectors; the hotspot schedule directed 70% to one sector/chunk. The deterministic target action and subscription schedules matched across protocol modes. Trial 1 ran baseline → 20 ms → 50 ms; trial 2 reversed the mode order. The 20-second workload requested 250 actions/s (5,000 actions); the five-second burst requested 750 actions/s (3,750 actions). Burst testing began after the sustained instrumentation and smoke run succeeded.

Application frames and bytes are counted at client receive, including HELLO, snapshots, ACKs and deltas, **excluding Colyseus/WebSocket framing and TCP/IP bytes**. CPU seconds are cumulative per process over connection, action and verification phases; RSS is a point-in-time process reading. Client ACK p95 covers all acknowledged actions in successful cases. Visible p95 samples only applied actions by 20 instrumented actors (not every recipient); raw artifacts give sample counts, p50/p95/p99, server phase histograms, queue depth and event-loop lag. Failure artifacts contain partial counts and are not comparable as full-run traffic totals. `docs/benchmarks/M26_1000_*.json` contains all 24 trials, including both failures; `M26_100_hotspot_5s_250r_batch20_trialsmoke.json` is the earlier smoke run.

Values are the **range across two independent trials**. Frame and byte counts include all received application frames. ACK and visible values are p95 milliseconds. Every row applied or acknowledged all 5,000 actions, reached exact final mask/fog convergence, and observed zero client errors, resyncs and missing sampled own deltas.

The hotspot's 1,182,338 delivered revision records were identical across modes. Against baseline, the 20 ms batches reduced received frame count about **71.6%** and application bytes about **54.7%**; 50 ms reduced them about **81.5%** and **60.3%**. On balanced traffic, 20 ms saved about **8.8% bytes** but almost no frames, while adding CPU and substantially delaying visibility. The 50 ms window saved about **18% frames / 15% bytes** in balanced traffic at still higher visible latency. Hotspot batch runs sustained the requested rate; the two baseline runs eventually received all ACKs but needed about 22.2–22.5 seconds to receive them, yielding roughly 222–225 acknowledged actions/s. Server command-receive-to-ACK-enqueue p95 for those baseline runs remained about 8.4–8.6 ms, locating most observed client delay after that phase or in shared-host scheduling.

The sustained hotspot 20 ms batch trial 1 used about **346 MiB server RSS** versus **243 MiB** for its per-action counterpart; 50 ms used about **326 MiB**. These snapshots include runtime/GC timing and are not a stable heap budget. The batcher's per-session timers and retained records warrant profiling before adoption.

All ten successful burst cases converged exactly with zero observed errors/resyncs/missing sampled own deltas. Both v1 hotspot bursts hit the 20-second ACK timeout, so no final convergence claim is made for them. Batching materially reduced outbound work under this specific fanout shape, but the balanced and visibility tradeoffs remain.

## Correctness, compatibility and decision

Focused tests cover v1/v2 envelope compatibility, ordered records including repeated same-tile updates, atomic school-bit validation, duplicate and gap handling, mixed v1/v2 subscribers, private ACK timing, synthetic school isolation, resync and reconnect while a batch is pending. The successful network loads also verified final projected mask/fog equality for every subscribed client. The repeated same-tile record test is a codec/replica test: the synthetic EXPLORE fixture only sets presence, so the load scenario does not exercise toggling the same tile. Automated resync fallback was exercised by unit tests rather than by an induced packet gap in the network load.

Strict TypeScript compilation, lint, client build and the full PostgreSQL-backed branch suite passed: **23 tests, 0 failures, 0 skips**. Branch size after the experiment: **26 first-party source files / 109,168 bytes**, **7 test files / 52,944 bytes**, **10 scripts / 50,731 bytes**; client bundle **535,507 bytes raw / 133,887 bytes gzip**. The bundle stays essentially unchanged because this server-side candidate is not used by the production client fixture. No dependency was added for M2.6.

**Decision: retain batching as an experimental, opt-in branch; do not replace the default v1 protocol.** The measured hotspot gains support further evaluation, but they do not prove 10,000-CCU readiness or production safety. Both processes shared one host and loopback sockets; application byte counts omit framing; synthetic clients are not browsers; the M2 fixture has no durable M3 transaction cost; and the 20-second v1 hotspot baseline was markedly slower than the earlier M2.5 same-host result. This run-to-run host sensitivity limits any capacity inference. Next validation should use a separate generator host, representative browser clients, longer sustained periods, induced disconnect/resync under load, network byte counters, and memory profiles. Do not add Redis or distributed sector writers from these results.

**M4 readiness recommendation:** M3's durable foundation has been technically accepted, but M4 remains unauthorized. Production identity, command/rule and C-08 visibility approval, plus review of the M3.5 durable hotspot capacity risk, are required before a playable production slice. No experimental batching code has been merged into the baseline.
